# 201 / 51 Pilot Competitive Experience Blueprint v1.0

**Mission:** `C004`
**Scope:** Stainless round pipe, grade 201, diameter 51 mm
**Status:** Blueprint only
**Implementation / population authority:** None

## 1. Boundary

This blueprint applies competitive intelligence to a future customer experience.
It does not select a C002 Pilot candidate, create a Product/SKU/Availability/price,
promote any of the 216 C003-R3 evidence positions, or start C003-A/C003-B.

Current evidence remains:

- Product Data Completeness: `SUBMITTED / OPEN_BLOCKING`;
- C002 readiness: `0/9`, `NOT_READY`;
- commerce: `INQUIRY_ONLY`;
- Mass and supply intake: empty;
- Runtime and production authority: none.

## 3. Interaction principles

### Mobile First Persian RTL

- one primary question per step;
- selected context remains visible and reversible;
- large touch targets and Persian RTL reading order;
- technical details available on demand, not hidden permanently;
- unknown, incompatible and verification-required states have distinct wording;
- no desktop mega-menu or dense table is required to complete selection.

### Data-rich without overload

The compact surface may progressively reveal:

- canonical identity and selected attributes;
- dimensional context and unit;
- technical notes from authoritative Knowledge owners;
- Mass context only after approved provenance;
- supply state only after dated, valid evidence;
- inquiry/commercial CTA from operator authority.

It does not copy a competitor's table. It projects Damavand-owned facts into an
original staged experience.

### Inquiry and trust

The CTA must state what happens next: submit context, specialist/operator verifies,
and the customer receives a governed response. It must not imitate checkout when
checkout is disabled. A future Availability message cannot say “in stock” merely
because a source is routinely available.

## 4. Supporting experience

### Technical information

Candidate Knowledge links, each with its own canonical intent owner:

- grade 201: scope, common use and selection limitations;
- 201 vs 304 comparison;
- how diameter and wall thickness affect application;
- how Mass is determined and why observed values vary;
- natural stainless vs gold/PVD appearance semantics;
- branch length, cutting and operator confirmation;
- how to prepare an inquiry for a railing project.

### Related 38 / 16 context

The Founder-confirmed current-intent `51 + 38 + 16` consumption evidence can
trigger a neutral question such as
“Are you planning a railing system that also uses smaller components?” It cannot
preselect quantities, assert compatibility, claim stock, calculate price or add a
bundle. Future suggestions require Product relationships, Inventory Harmony,
current evidence and operator review.

## 5. Fast Track experience requirement

The smallest useful future slice would prove:

1. family entry and dependent selection reduce discovery friction;
2. evidence-backed options prevent invalid inquiries;
3. one compact summary is understandable on a narrow RTL viewport;
4. inquiry context reaches an operator without pretending to be checkout;
5. original technical links answer the next common question;
6. measurement captures task completion, blocked states and operator correction.

This is a future acceptance hypothesis, not implementation authority.

## 6. SEO competitive blueprint

### Intent ownership

| Surface | Primary search intent | Candidate canonical role | Indexing posture |
|---|---|---|---|
| Product family page | Discover stainless round pipe | Broad commercial family owner | Index candidate after Product/SEO gates |
| Grade page | Understand/shop grade 201 within the family | Grade-aware commercial landing | Only if it has unique demand and content |
| Size page | Find 51-mm commercial context | Size-intent landing linked to family | Candidate; never auto-generated for every size |
| Commercial Product page | Select and inquire for the governed family context | One Product intent owner | Canonical; no page per arbitrary tuple |
| Knowledge page | Learn 201 vs 304, thickness, Mass or application | Separate educational intent owner | Index candidate with authoritative review |
| Comparison content | Compare material/grade/application choices | Knowledge/comparison owner | Unique evidence and review required |
| Calculator/support page | Solve a weight or project-support task | Future tool intent owner | No calculator page before tool/data authority |

### Crawlability and faceted navigation

- Canonical Product Data may be projected into crawlable HTML after separate gates.
- Selector state and query parameters do not automatically become indexable pages.
- Facets default to non-indexable unless a separately reviewed unique intent owner exists.
- Canonical candidates should collapse equivalent selector and campaign URLs.
- Sitemaps include only approved canonical owners, not every combination.
- Structured Product Data cannot contain Offer/price/Availability until separately authorized.

### Internal linking

- family → grade/size commercial owners where unique;
- commercial owner → relevant technical guidance;
- knowledge → one primary commercial owner plus contextual related guidance;
- 51 context → neutral 38/16 application learning, not an automatic bundle;
- calculator/support → authoritative input definitions and relevant family owner.

### Thin-page and cannibalization prevention

Do not publish separate pages for every brand, thickness, finish, length or filter
permutation. A page must have unique intent, governed evidence, original useful
content and one owner. Otherwise the information belongs in the family selector
or canonical Product detail.

### Long-tail strategy

Long-tail size/thickness language may inform search aliases, FAQs, selector copy
and reviewed knowledge topics. It cannot create a Product value, tuple or page by
itself. Competitor terms are discovery input only; Damavand wording must be
original, technically reviewed and aligned with canonical labels.

## 7. Future acceptance checks

A separately authorized implementation Mission would need to prove:

- every selectable state resolves to canonical evidence;
- no unsupported combination is selectable or indexable;
- Product, Mass, supply, Availability, price and operator states stay separate;
- current mode remains inquiry-first unless per-SKU gates pass;
- keyboard, screen-reader, mobile RTL and performance checks pass;
- structured data contains no unauthorized Offer/Availability;
- content is original and source-governed;
- analytics collect no unapproved PII and create no CRM authority.
