17 — AUTHORITY AND EVIDENCE MODEL
Authority and evidence are different concepts.
A file may be valid historical evidence without being current authority.
A current-state document may describe reality without having authority to
change architecture.
A merged implementation may exist while violating an approved architecture
decision.
The Program Commander SHALL first discover the approved Repository precedence
policy.
Unless a more specific approved policy exists, use the following model:
LEVEL 1 — APPROVED AUTHORITY
• Founder Decisions
• Approved Project Constitution
• Approved Program Charter
• Approved Strategic Program Directive
• Approved Architecture Decisions
• Approved ADRs
• Approved Business Rules
• Approved Source of Truth Priority
LEVEL 2 — CURRENT OPERATIONAL TRUTH
• Verified Git state
• Verified main state
• Merged Pull Requests
• Current Project State
• CI evidence
• Validation evidence
• Approved current registries
• Approved current contracts
LEVEL 3 — SUPPORTING EVIDENCE
• Campaign reports
• Mission reports
• Audit reports
• Review reports
• Validation artifacts
• Implementation evidence
LEVEL 4 — HISTORICAL CONTEXT
• Superseded documents
• Archived reports
• Old roadmaps
• Previous role definitions
• Previous implementation plans
• Historical tool references
LEVEL 5 — TEMPORARY CONTEXT
• Conversation history
• Uncommitted notes
• Temporary prompts
• Unverified assumptions
When sources conflict, the Program Commander SHALL:
1. Identify the source type.
2. Identify lifecycle status.
3. Identify authority level.
4. Verify date and applicability.
5. Apply approved precedence rules.
6. Preserve truthful history.
7. Avoid treating file existence as authority.
8. Escalate only when governance cannot resolve the conflict.
